## 1. 背景与目标

### 现状（代码核实，非文档描述）

- `netsock.c` 协议层**直接调用** `e1000_tx/rx/mac/gw_mac/ready` 等驱动函数，协议层与具体网卡驱动强耦合；
- `netsock.c:99` `udp_build_frame` 在协议层**自己拼装完整以太网帧**（eth + IP + UDP 三层头），抽象点目前在驱动层而非协议层；
- 换网卡 = 改协议层代码，不可接受。

### 目标

1. **引入 netif 抽象层**：系统代码不依赖具体网卡，统一走接口；网卡变了主体代码不改。
2. **串口抽象成网卡**：COM2 串口用 SLIP 封装（RFC 1055），成为与 e1000 平级的第二个 netif 后端。
3. **间接实现 TCP（薄包装起步）**：guest 内只有 UDP 数据报语义，宿主转发器完成 UDP↔TCP 映射；guest 应用通过"虚拟 TCP API 薄包装"获得 TCP 风格调用。
4. **为薄→厚演进预留架构**：连接句柄、流式缓冲、控制/数据通道、协议头版本等接口现在就设计对，将来升级厚包装（本地伪状态机）不改应用代码、不返工。
5. **兼容未来 HAL**：netif ops 表就是 HAL 设备表原型，HAL 落地时零返工并入 `hal_register(device_class_net, &ops)`。

### 明确不做（范围排除）

- **guest 内完整 TCP 协议栈**（内核态或用户态真 TCP：状态机/重传/流控/拥塞）——复杂度与测试面超纲，不现实，本路线图及后续演进**均排除**。
- 演进天花板 = **厚包装**（guest 侧本地伪状态机：序列号/超时重传/乱序缓冲/伪 ACK），见 §4.1。若未来确有真 TCP 需求，那是另起炉灶（virtio-net 模式）的独立项目，不在本路线图内。

## 2. 架构决策（已对齐，不再讨论）

| # | 决策点 | 结论 |
|---|--------|------|
| D1 | 抽象层包单位 | **IP 数据报层**（lwIP netif 模式）。不做以太网帧层——串口无以太网语义，SLIP 就是 IP over 串口，做帧层会欠"假 MAC + 假 ARP"的技术债 |
| D2 | netif 接口形态 | **ops 表**（init/ready/tx/rx/mac），注册表模式，协议层只依赖接口。= 未来 HAL 设备表原型 |
| D3 | 串口网卡端口 | **COM2**（QEMU 第二个 `-serial`）。COM1 已被 shell 终端占用，严禁复用 |
| D4 | 虚拟 TCP 起步档位 | **薄包装**（见 §4）。demo 场景 = HTTP 请求-响应，薄包装够用；**架构按薄→厚演进预留**（见 §4.1），厚包装列为可选项，跑通 demo 后再评估 |
| D5 | TCP 语义执行位置 | **宿主转发器**。真 TCP 状态机只在宿主；guest 侧不实现完整 TCP 栈（§1 范围排除），演进上限 = 厚包装伪状态机 |
| D6 | 网卡选择策略 | **静态绑定**（编译开关/启动参数）。mini-os 无路由表，不实现完整路由；netif 层只留"选择策略"接口，将来要按目的 IP 选路可平滑升级 |

### 目标架构

```
guest（内核）
  app → 虚拟 TCP API（薄包装：tcp_open/send/recv/close 方法函数）
      → 会话协议（UDP 载荷：会话 ID + 消息类型 + 版本 + 数据；§3 Step 4）
      → UDP 数据报（统一载体，所有虚拟 TCP 流量都封装成 UDP）
      → netif 抽象层（ops 表：init/ready/tx/rx/mac）
      → { e1000 网卡（现有） | COM2 串口网卡（SLIP, RFC 1055） }
宿主
  → 转发器（Python，有状态协议转换网关）
      → TCP 映射（真 TCP 状态机在宿主）
      → UDP 直转（对 UDP 服务原样转发）
```

**关键澄清**：虚拟 TCP 不直接走串口。串口网卡与 e1000 是平级物理通道，统一挂 netif 下；虚拟 TCP 的载体永远是 UDP 数据报，走哪个网卡由 netif 决定。串口上跑的是 SLIP 封装的 IP（UDP 报），不是 TCP 协议帧。

## 3. 落地路径（四步，每步可独立验证）

### Step 1：netif.h/c + e1000 薄封装（纯重构）

- 新增 `src/net/netif.h` / `netif.c`：
  - 定义 ops 表：`netif_ops { init(); ready(); tx(frame,len); rx(buf,max); mac() }`；
  - 提供注册与选择机制（当前单网卡，注册表按序取第一个即可；选择策略接口预留，见 D6）；
  - 统一收包缓冲接口，供协议层轮询读取。
- 新增 `src/drv/e1000_netif.c`（或改造 e1000.c）：把现有 e1000 驱动函数包进 ops 表，**驱动本身不改逻辑**。
- 协议层改造：`netsock.c` 从直调 `e1000_tx/rx` 改为调 netif 接口；`udp_build_frame` 的 eth 头拼装从协议层下沉到 e1000 适配层。
- **验收**：CI 全绿（test + 7×layer）；QEMU 起 guest，现有 UDP demo（如 echo/socket 自测）行为与改造前一致；diff 应为纯重构（协议语义零变化）。

### Step 2：COM2 串口适配器（SLIP）

- QEMU 启动脚本加第二个 `-serial file:...` / `-serial tcp:...`（COM2）。
- 新增 `src/drv/uart_netif.c`：实现 SLIP 封装/解封装（RFC 1055：END 0xC0、ESC 0xDB、ESC_END 0xDC、ESC_ESC 0xDD），包进 netif ops 表注册为第二个网卡。
- 现有 UDP 收发包在 COM2 串口链路打通（guest ↔ 宿主串口对端）。
- **验收**：guest 内 UDP 数据报经 COM2 串口到宿主串口对端，收发往返一致；SLIP 帧边界、转义字节（含数据中出现 0xC0/0xDB 的用例）测试通过；CI 新增串口网卡单测。

### Step 3：协议层彻底走 netif（eth 封装下沉收尾）

- 核对协议层不再出现任何 eth 头 / e1000 直调符号；IP 数据报为 netif 统一包单位。
- 网卡选择逻辑：默认 e1000；串口网卡按编译开关或启动参数绑定（demo 用）——静态绑定即可，**不实现路由表**。
- **验收**：`grep e1000 src/net/` 为空；CI 全绿；任意换网卡（编配串口版）协议层零改动。

### Step 4：宿主转发器 + 虚拟 TCP demo

- **会话协议头**（薄包装与转发器之间，UDP 载荷前部；**关键预留点**）：
  - `session_id`（连接句柄的线上标识）+ `msg_type`（数据/事件：连接建立、对端关闭、失败、超时）+ `version`（协议版本，**必须存在**）+ `flags`（保留，厚包装加序列号/ACK 用）+ 载荷；
  - 设计原则：**消息类型与数据分离、版本字段先行**——未来厚包装新增字段不改帧格式，转发器按 version 分发处理，新旧会话共存。
- 宿主侧新增转发器（建议先 Python，逻辑清晰可测；socat 只作 1:1 对照，不作主力）：
  - 监听串口对端（或 e1000 侧 UDP 端口）；
  - **TCP 映射**：按 `session_id` 维护 UDP 会话 ↔ TCP 连接映射（有状态网关：会话表 + 超时清理 + 半开连接处理 + 背压）；
  - **UDP 直转**：目标为 UDP 服务时原样转发；
  - **事件回传**：连接建立/对端关闭/失败/超时通过 `msg_type=event` 回传 guest（薄包装的失败感知来源，见 §4）。
- guest 侧新增虚拟 TCP 薄包装 API（libc 层或用户库）：
  - `tcp_open(ip,port)` / `tcp_send(fd,data,len)` / `tcp_recv(fd,buf,max)` / `tcp_close(fd)`；
  - **fd 背后必须是"连接对象"结构**（含 session_id、状态、发送队列/接收缓冲、事件队列），不是裸整数——厚包装时同一对象加状态机字段即可（见 §4.1 预留点 1/2）；
  - 内部：调用封装成会话协议报文，走 netif；应答与连接状态由事件/超时感知。
- **验收**：demo 跑通——guest 内发起 HTTP 请求（薄包装 API），经 netif（串口或 e1000）→ 宿主转发器 → 真实 HTTP 服务，回包正确展示；断连/超时场景有明确失败返回值，无挂死。

## 4. 虚拟 TCP 语义边界（薄/厚两档）

**诚实声明：这是包装，不是 TCP。** 应用体感取决于包装厚度：

| | 薄包装（本路线图目标） | 厚包装（演进上限，§4.1） |
|---|---|---|
| guest API | tcp_open/send/recv/close | 同左，签名不变 |
| 底层 | UDP 数据报 + 宿主代理 | 薄包装 + 本地伪状态机（序列号/超时重传/乱序缓冲/伪 ACK） |
| 应用体感 | "调用像 TCP"，语义仍是请求-应答（一次 send 对一次 recv） | 接近真 TCP |
| 丢包/断连 | 超时感知 | 重传兜底，应用基本无感 |
| 适用 | HTTP 请求-响应 demo | 流式/长连接场景 |
| 成本 | 低 | 高，测试面显著增大 |

TCP 给应用的三个体感来源，薄包装只给三分之一：**流式**（薄包装做不到，仍按报文）、**可靠**（重传在宿主做，guest 无感）、**状态可见**（guest 只能靠返回值推断，除非转发器显式回传连接状态事件）。

→ 转发器需提供"连接失败/超时事件"回传通道（Step 4 的 `msg_type=event`），这决定薄包装的体验下限。

### 4.1 架构预留：薄 → 厚演进（本路线图的长期接口契约）

**目标**：将来升级厚包装时，**应用代码零改动、协议帧格式不破坏、转发器新旧会话共存**。以下接口现在就必须按此设计：

1. **连接句柄 = 对象而非整数**：`tcp_open` 返回的 fd 映射到"连接对象"（session_id、状态、收发缓冲、事件队列）。厚包装只是给同一对象加状态机字段，API 签名不变。
2. **收发走流式缓冲**：`tcp_send/recv` 内部一律经"发送队列 / 接收缓冲"，薄包装一次 send=一条报文，但数据结构按流式设计（可拼接/可分段）。厚包装的乱序缓冲/重传队列直接复用。
3. **控制/数据通道分离**：会话协议头 `msg_type` 区分数据与事件（建立/关闭/失败/超时）。薄包装已具备事件感知，厚包装的事件驱动天然可用，无需改协议。
4. **协议头版本字段先行**：`version + flags` 必须占位。未来加序列号/ACK 字段不改帧格式，转发器按 version 分发（旧薄会话与新厚会话并存）。
5. **转发器保持无状态协议、可扩展**：转发器只按 `session_id + version` 工作，不假设"每 session 必为请求-应答"；厚会话只是载荷里多了字段，转发路径不变。

**一句话**：薄包装是"API 形状 + 事件通道"先立起来，厚包装是"在既有对象和通道里补状态机"——架构上不堵路。

## 5. 红线与约束

1. **不实现完整 TCP 栈**（内核态或用户态）——真 TCP 状态机只在宿主转发器；guest 侧演进上限 = 厚包装伪状态机（§4.1），到此为止。
2. **串口网卡只用 COM2**，COM1 是 shell 终端，严禁占用/改动。
3. 不引入假 MAC / 假 ARP 语义（选 A 方案的动机）。
4. 每一步必须 CI 全绿才能进下一步；Step 1 是纯重构，禁止夹带行为变更。
5. 驱动层（e1000）只做薄封装，不改原有收发逻辑。
6. **不实现路由表**：网卡选择为静态绑定（D6）；§4.1 预留点仅指"接口形状"，不扩大 Step 3 范围。
