# minicc V3 后续任务简报

> 发件：架构侧。收件：dev。
> 起点：`feat/minicc-v3-selfhost` @ `372ca52` 已实测全绿（`make -Werror` / `test_miccboot.sh` P1==P2 / `test_serial.sh` / `test_minicc.sh` 宿主 44 + guest 端到端）。自举不动点已锁定。
> **通用原则：以下每项的"参考路径"只是方案选项与权衡信息，不是指令。实现方式、命名、拆分粒度均由你判断。**

## 任务 1（P0，成本最低）：GVAR hex 初始化器回归用例——锁定 BUG-039

**目标**：给 BUG-039 的修复加测试，防止回归。

**背景**：BUG-039（GVAR 十进制环把 `0x800a0000` 的 `x`/`a` 当数字位，算出 `0xB1F37610` 垃圾值，导致自举 CODE_BASE 崩坏）已在 `minicc.c` 修复，但 `test_minicc.sh` 目前只有**表达式层** hex（`t_hex`：`0x10/0xff/0x0a`）和 guest 位运算+hex（`0x30`），**没有 `int G = 0x800a0000;` 形态的 GVAR 初始化器用例**。这个 bug 是 P1==P2 的关键前提，值得一条测试锁死。

**参考路径**（仅供选择）：
- 宿主一条：`int G=0x800a0000;` + 运行语义断言 `G==2148139008`（比"compiled OK"更强，能抓住值错）；
- guest 一条对应用例（注意沿用现有的 <128B 或 heredoc 约定）；
- 可顺带决定是否覆盖 `0X` 大写前缀、hex 回绕边界（`0xFFFFFFFF`）——你判断值得覆盖哪些。

**验收建议**：新用例在当前代码通过；**临时回退 BUG-039 修复时该用例必须 FAIL**（自证测试有效性，与项目防假绿哲学一致）。

## 任务 2（P1）：文档 §6.2 帧布局措辞与实现对齐（F9）

**目标**：消除文档与实现的表述分歧。

**背景**：§6.2 写「标量 4 字节对齐」，但实现是**纯字节偏移**分配（实测：`char s[3]` 后 `int x` 落 `-7(%ebp)`，未对齐 4 边界）。x86 非对齐访问容错，guest 实测无碍，所以这是**措辞失准**而非功能 bug。

**两个方向及其权衡**：
- **(a) 改文档如实描述**（字节偏移、未对齐，x86 允许）：零风险，推荐起点；
- **(b) 改实现对齐到 4 边界**：更"整洁"且利于未来移植，但改变已验证的帧布局行为，需全量回归，且对当前单目标（i386）收益有限。

**验收**：文档描述与代码行为完全一致，第三方读文档能准确预测帧布局。

## 任务 3（P1）：writefile 长单行限制——确认现状（F10）

**目标**：确认该限制在 V3 的状态并记录，而不是盲目修。

**背景**：V2d 时代实测 shell `writefile` 内建对 ≥~100 字符单行写入损坏（症状：后续 `minicc: input open fail`）。V3 的 `shell.c` 新增了 heredoc 支持（`test_serial.sh` 的「writefile heredoc 写多行」已通过），所以现在可能是：已修复 / 被 heredoc 绕过 / 仍存在但无测试触碰——三种状态对应三种不同处置。

**参考路径**：
- 若已修复：加一条长单行用例锁定，关闭 F10；
- 若靠 heredoc 绕过：在文档/脚本注释标注「单行 writefile 限制 X 字节，用 heredoc 替代」，让后来者不再踩坑；
- 若仍在且会坑人：修或限长报错（拒绝静默截断）由你判断。

**验收**：现状有明确定论 + 有测试或文档记录，不再依赖口口相传。

## 任务 4（P2，规划项）：Mock AST 单测落地（F2，原则 6）

**目标**：让设计文档原则 6「完全采纳 Mock AST 单测」名实相符。

**背景**：`tests/utest.h` 已存在，`minicc.c` 未使用，当前测试纯黑盒（编译→跑→断言）。黑盒已很强（44+guest+miccboot），单测的增量价值主要在：错误路径精细断言、重构时的快速定位（配合任务 5）。

**需要你权衡的点**：
- `minicc.c` 是单文件、全量全局、`minicc_main` 特化入口——引入单测需要决定链接方式（如测试 driver `#include minicc.c`，或提取可测层）；
- **注意与任务 5 的联动**：如果先做 CompilerContext 收敛，单测的注入点会完全不同。两者做的顺序值得你先想清楚；
- 另一个合法解法是**修订原则 6 的表述**（承认当前以黑盒为主、Mock 单测列为演进项）——"文档对齐实现"同样是还债，成本趋近于零。选哪条路由你定。

**验收**：原则 6 名实相符（有单测，或文档如实描述现状与计划）。

## 任务 5（P2，规划项）：CompilerContext 收敛（F3，§10.1）

**目标**：兑现 §10.1「V2 起收敛 CompilerContext、不再新增全局可变状态」。当前仍是 V1 式全量全局（`tok/src/syms/patches/labs/code/...` 约 20+ 个）。

**为什么现在是候选窗口**：自举不动点已锁定，三重回归网（miccboot + 宿主 44 + guest 端到端）是做无行为变化重构的安全网。越晚做，新代码挂在全局上的面越大。

**需要你权衡的关键约束**（这是本任务最微妙处）：
- `minicc.c` 与 `minicc_self.c` 存在**行为严格一致纪律**（BUG-039 注释即写明"与 minicc_self.c 的 GVAR 初值环严格一致"）；
- 若引入 `struct CompilerContext`：`minicc.c`（gcc 编译，全语法）没问题，但 `minicc_self.c` 必须落在 minicc 支持子集内——**minicc 不支持 struct**。对应路径有二：自举版用并行数组/指针模拟 context（保持子集纪律），或两版暂时不同构但语义严格一致（纪律从"结构一致"退化为"行为一致"，是否可接受由你定义）；
- 纯重构 = 无行为变化：验收即全部既有测试零改动通过（或仅因新增断言而通过）。
- 也可考虑分步：先收拢最内圈状态（词法/符号表），code buffer 与 patch 体系后置。

**验收**：P1==P2 仍逐字节一致；44+guest 全绿；全局可变状态数量有可核对的下降。

## 任务 6（P3，单独立项）：cc500 退役路线（F6）

**目标**：把「替代 GPL cc500」从能力达成推进到决策落地。minicc 已自举（能力条件具备），但 initramfs 仍嵌入 `cc500.c` blob（`tools/cc500/`、`test_cc500.sh`、shell 的 ccboot 链路都在）。

**这不是删文件**，需要先回答两个前置问题：
1. **许可核实**：cc500 的实际许可证条款是什么？MIT 项目嵌入/分发 GPL 代码的兼容性如何处理（替代目标本身暗示了许可动机，值得把结论写进 ADR）；
2. **依赖盘点**：哪些测试/命令/文档仍引用 ccboot/cc500（如自举对照、教学对照）。

**参考路径**：(a) 分阶段退役——miccboot 升为默认自举路径，ccboot 降级为可选对照，最终移除；(b) 保留为历史/教学对照但明确许可边界。建议产出一份 ADR（状态、决策、后果）再动仓库。

## 项目既有纪律提醒（跨任务适用）

1. **防假绿**：错误路径断言用症状对立（不得出现成功标志），成功路径断言运行语义而非编译产物存在；
2. **子集纪律**：`minicc_self.c` 任何改动不得超出 minicc 支持子集（违规即 bug）；
3. **双源一致**：`minicc.c` 行为变更需同步 `minicc_self.c`（反之亦然），P1==P2 是最终裁判；
4. **文档随码**：行为变更同步 `docs/design/minicc-design.md`（含 BUG 编号、roadmap 状态）；
5. **长任务后输出运维记录**，敏感操作前对齐。
